## Username or email? (checked first)
🔵 Supabase password sign-in identifies a user by **email or phone number** (`signInWithPassword({ email | phone, password })`, Supabase "Password-based Auth" guide). There is **no built-in username login**.

A username login would need custom code: store a `username → user` mapping, look up the email on the server, then sign in with it. That:
- adds a public lookup that reveals whether a username exists (account enumeration);
- still needs an email address for confirmation and password reset;
- is more code to secure.

➡️ Per D35's preference, **email + password** is used. No usernames.

## What was built (web app, `apps/web`)
| Flow | How it works |
|---|---|
| Sign up `/sign-up` | Email + password + confirm. Password rule: ≥ 10 characters, letters and digits, ≤ 72 bytes (bcrypt limit). Same answer for new and existing emails ("check your inbox"). |
| Confirm email | Email links go to `/auth/confirm?token_hash=…&type=email`. The token is used **only when the person presses the button** (a POST), so email scanners that pre-open links can't use it up. Then they land in `/workspace`. |
| Sign in `/sign-in` | Email + password. One message for wrong email or wrong password. Unconfirmed accounts are told to confirm first (only shown after a correct password). `next=` is limited to same-site paths (open-redirect protection). |
| Sign out | Server action; ends this browser's session and clears cookies. |
| Forgot password `/forgot-password` | Same answer whether or not the account exists. |
| Reset password | Email link → `/auth/confirm?…&type=recovery` → button → `/reset-password` (needs the recovery session). Saving signs out **all other sessions**. A "password changed" notice email is sent. Reusing the same password is refused. |
| Session handling | `@supabase/ssr` keeps the session in cookies. The Next.js 16 proxy (`proxy.ts`) refreshes it on every request and redirects people in the wrong place. Protected pages verify the user again with `getClaims()` (signature check against the project's keys), so a proxy mistake can't expose a workspace. |
| Protected page `/workspace` | Shows the signed-in email and calls the API's `/me` with the user's access token to prove the API accepts it. |

Security choices:
- **All auth calls run on the server** (server actions). No browser-side Supabase client, so the session cookies are **HTTP-only** and `SameSite=Lax`; scripts in the page can't read tokens. Next.js server actions reject cross-site calls.
- Env vars renamed to server-only names: `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `EXPLORAAI_API_URL` (no `NEXT_PUBLIC_`).
- Security headers on every page (`nosniff`, `X-Frame-Options: DENY`, referrer policy, permissions policy). `/auth/*` pages send `Referrer-Policy: no-referrer` and `no-store`, so the one-time token never leaks or gets cached. A full Content-Security-Policy comes with the design system in M8.
- Logs record action + error code only; never emails, passwords or tokens.

Libraries: `@supabase/ssr` 0.12.7, `@supabase/supabase-js` 2.117.3 (picked over 2.118.0 for a longer public soak), dev-only `playwright-core` 1.56.1 (matches the installed Chromium). Trivy: no HIGH/CRITICAL findings.

## API (`apps/api`)
JWT verification kept and extended:
- Algorithm (ES256/RS256 only; HS256 and `none` refused), issuer, audience, expiry, issued-at, subject, role, all checked.
- **New:** tokens of anonymous users (`is_anonymous`) are refused.
- **Key rotation, now tested end to end** with the real JWKS client against a local key server:
  - a newly published signing key is picked up without a restart;
  - 🔵 **finding:** PyJWT refetches keys for an unknown key ID at most once every 30 seconds. This is kept on purpose: 20 forged key IDs caused **zero** extra fetches in the test. Supabase publishes a new "standby" key before signing with it, so real rotations aren't affected if the steps below are followed.
  - keys unreachable → 503 (fail closed).
- **New per-user authorization rule** (`authz.py`): every query filters by the verified user ID; `ensure_owner()` returns **404** for someone else's resource, so IDs can't be probed. RLS still applies underneath.

## 🟠 Known limits
- After a password reset, other devices can't refresh their session any more, but an access token they already hold stays valid until it expires (Supabase default 1 hour). This is how stateless JWTs work. Option: shorten the JWT expiry on the hosted project (e.g. 15 minutes), at the cost of more refreshes.
- Supabase Auth rate limits are per IP. Because sign-in runs on the web server, users share the server's IPs in those limits. Fine for a small beta; revisit (raise limits or add app-side limits) before wider use.
- "Leaked password" checking (HaveIBeenPwned) is a Supabase Pro feature, so it isn't available on the free plan (D33).
